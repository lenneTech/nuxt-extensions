# Migration Guide: 1.x → 4.0.0

**New version scheme, three changed defaults.** 4.0.0 follows 1.28.0 directly. Nothing was
rewritten: it is 1.28.0 plus the three changes below. Most projects created from
nuxt-base-starter 2.38.5 or later update without touching anything.

## The version scheme

From 4.0.0 on, the major of `@lenne.tech/nuxt-extensions` is the Nuxt major, the same scheme
`@lenne.tech/nest-server` (major = NestJS) and `@lenne.tech/ng-base` (major = Angular) use:

| Part | Meaning | Example |
|------|---------|---------|
| **MAJOR** | The Nuxt major the module is built for (`@nuxt/kit ^4`, peer `nuxt ^4.0.0`). It moves only with Nuxt. | `4.x.x` = Nuxt 4 |
| **MINOR** | A change you have to act on when you update: behaviour, code or configuration. Every breaking change is a minor, with a migration guide. | `4.1.0` |
| **PATCH** | A fix or addition you can take as it is. | `4.0.1` |

**2.x and 3.x are skipped on purpose.** They were never published. 1.x already was the Nuxt 4 line,
but its major did not say so; 4.0.0 makes the number match. Nothing between 1.28.0 and 4.0.0 is
missing.

**Pin the exact version**, as the starters do. A caret range (`^4.0.0`) pulls in minors, and under
this scheme a minor is exactly the change you have to act on. Update on purpose, with the migration
guide of each minor.

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | The default TUS endpoint is `/tus` (was `/files/upload`). `auth.enableAdmin` defaults to `false` (was `true`). `useLtFile()` builds its file URLs on the API, the links point at `GET /files/id/:id`, and `getDownloadUrl()` ignores `filename`. |
| **New** | A one-time console warning when `enableAdmin` is on but the API reports no admin plugin. |
| **Migration Effort** | Usually none for projects from nuxt-base-starter 2.38.5 or later. A project from an older starter deletes `enableAdmin: true`. A project with its own same-origin proxy for `/files` sets `resolveAgainstApi: false` and serves `/files/id/:id`. |
| **Cross-repo** | `GET /files/id/:id` needs nest-server 11.8.0 or later. `/tus` is nest-server's TUS path unless its `tus.path` is changed. nuxt-base-starter 4.0.0 uses this version. |

## Steps

### 1. Update

```bash
pnpm add @lenne.tech/nuxt-extensions@4.0.0
```

Vendored projects: update the core (`/lt-dev:frontend:update-nuxt-extensions-core`).

**Coming from a version before 1.28.0:** apply the guides of the versions in between first, oldest
first (`1.22.x-to-1.23.0.md`, `1.25.x-to-1.26.0.md`, …), and the one step of 1.28.0: npm-mode
projects that use `LtTransitionFade` / `LtTransitionFadeScale` add
`@source '../../../node_modules/@lenne.tech/nuxt-extensions/dist/runtime';` to the stylesheet that
imports Tailwind (README, "Transition Components").

### 2. TUS uploads: `/tus`, or your own endpoint

`ltExtensions.tus.defaultEndpoint` defaulted to `'/files/upload'`, a path nest-server does not
serve. It is now `'/tus'`, nest-server's TUS path.

**Nothing to do** if your project sets `tus.defaultEndpoint` (nuxt-base-starter sets `'/tus'`) or
passes `endpoint` to every `useLtTusUpload()` call.

**Your backend serves TUS at `/files/upload`?** Keep the old value:

```ts
// nuxt.config.ts
ltExtensions: {
  tus: {
    defaultEndpoint: '/files/upload',
  },
},
```

or per stage: `NUXT_PUBLIC_LT_EXTENSIONS_TUS_DEFAULT_ENDPOINT=/files/upload`.

The base of the `useLtFile()` routes is unchanged: an endpoint ending in `/upload` sets it
(`'/api/files/upload'` → `'/api/files'`), any other endpoint, `/tus` included, leaves it at
`/files`.

### 3. File links: on the API, at `/files/id/:id`

`getFileUrl`, `getDownloadUrl` and `getFileInfo` now resolve like the auth, AI and TUS requests:
`NUXT_PUBLIC_API_URL` + path, or `/api` + path while the dev proxy is on. Before, they were paths on
the app origin and reached the API only behind a same-origin proxy.

| Helper | 1.x | 4.0.0 |
|--------|-----|-------|
| `getFileUrl(id)` | `/files/<id>` on the app origin | `<API>/files/id/<id>` |
| `getDownloadUrl(id, filename)` | `/files/download/<id>?filename=<filename>` | `<API>/files/id/<id>` |
| `getFileInfo(id)` | `GET /files/info/<id>` on the app origin | `GET <API>/files/info/<id>` |

The old link targets never worked against nest-server: it reads `/files/<id>` as a file **name**
(`GET /files/:filename`) and answers 404, and it has no `/files/download/<id>` route.
`GET /files/id/:id` (nest-server 11.8.0 or later) is the route that serves a file by its id.

**Nothing to do** if your project talks to nest-server directly and sets `NUXT_PUBLIC_API_URL`
(nuxt-base-starter does).

**Your project runs its own same-origin proxy for `/files`?** Keep the URLs relative:

```ts
// nuxt.config.ts
ltExtensions: {
  tus: {
    resolveAgainstApi: false,
  },
},
```

The option also keeps a relative TUS endpoint on the app origin, which is what such a proxy setup
wants. If the proxy served the old `/files/<id>` or `/files/download/<id>` paths, it now has to
serve `/files/id/<id>`.

**Code that passes a `filename` to `getDownloadUrl()`** keeps compiling, but the name is ignored.
nest-server never read the parameter; it sends the stored file name in `Content-Disposition`.

**Links are plain browser requests.** nest-server answers `GET /files/id/:id` only to the roles in
`file.downloadRoles` (default: admins). An `<img src>` or `<a href>` carries the session cookie when
app and API are on the same site (`app.example.com` / `api.example.com`), and never a JWT.

Two things that work without your help: the link helpers return the URL the browser uses, during
SSR too, so the server-only `NUXT_API_URL` never ends up in the HTML. And `useLtFile()` reads the API
base when it is called, so a link built after an `await` in `useAsyncData` still points at the API.

### 4. Admin client plugin: `enableAdmin: true` only with your own `admin()`

`auth.enableAdmin` defaulted to `true` and registered Better-Auth's admin client plugin in every
project. nest-server registers no server-side `admin()` plugin, so every `admin.*` call answered
404. It now defaults to `false`. `isAdmin` and admin UI gating are not affected.

**Projects from nuxt-base-starter before 2.38.5** set `enableAdmin: true` in `nuxt.config.ts`.
Delete the line, or set it to `false`. Otherwise the admin client plugin stays registered, and
`useLtAuth()` warns once in the console:

```
[LtAuth] ltExtensions.auth.enableAdmin is on, but the API reports no admin plugin (no `admin` in /iam/features). ...
```

**Your backend serves Better-Auth's admin routes?** Set `enableAdmin: true` and make its
`/iam/features` report `admin: true`; the warning stays off. Read "`admin.*` is passed through
UNHASHED" in CLAUDE.md first: `admin.createUser` and `admin.setUserPassword` are the only methods
this module does not hash, while every other password leaves the browser SHA256-hashed.

## Check after the update

- An upload goes to `<API>/tus` (or to the endpoint you set).
- A file link opens `<API>/files/id/<id>`.
- The browser console shows no `[LtAuth] ltExtensions.auth.enableAdmin is on` warning.
