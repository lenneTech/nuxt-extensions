# Migration Guide: 1.15.x → 1.16.0

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | **None.** The auth parameter types widened from closed shapes to generics, which accepts strictly more callers than 1.15.1 did. |
| **New Features** | `useLtAuth()` exposes `requestPasswordReset` and `resetPassword`. |
| **Bugfixes** | `changePassword` no longer drops `revokeOtherSessions`; `twoFactor.enable` no longer drops `method` and `issuer`. Both were silent. |
| **Migration Effort** | ~5 min to upgrade. Add ~20 min if your app passes either of the dropped options and you want to verify the fix, or if you have a hand-rolled reset page to retire. |
| **Cross-repo** | **No.** `@lenne.tech/nest-server` does **not** need to be upgraded. See below. |

---

## Before you start: this one is NOT a two-repo change

1.15.0 was, and its guide says so loudly. This one is not, and the difference is worth stating
because the CHANGELOG mentions `@lenne.tech/nest-server` 11.38.0 and that reads like a
requirement.

It is not one. Verified against the server:

- **`revokeOtherSessions` works against every nest-server version.** Better Auth reads and acts on
  it in its own `update-user` route; nothing in nest-server touches it. Until 1.16.0 the option
  simply never arrived.
- **The `twoFactor.enable` fields are the same story** — `method` and `issuer` are read by
  better-auth's own plugin.
- **The reset-path normalisation in nest-server 11.38.0 makes _plaintext_ clients fault-tolerant.**
  This library has always hashed, so that change is a no-op for it.

Upgrade this package on its own schedule.

## Steps

### 1. Update the package

```bash
# in projects/app
pnpm add @lenne.tech/nuxt-extensions@1.16.0
```

Nothing else changes. No config keys were added or renamed, no peer ranges moved.

### 2. Verify the two fixed defects, if your app passes those options

Both were **silent** — no error, no warning, and a green build. If your app never passes these
options, there is nothing to check.

**`revokeOtherSessions` on `changePassword`.** This is the one that matters, because it is what a
user sets after a suspected compromise:

```typescript
await changePassword({ currentPassword, newPassword, revokeOtherSessions: true });
```

Sign in from a second browser, change the password in the first with the flag set, then reload
the second. It must be logged out. Before 1.16.0 it stayed signed in while the UI reported
success — the caller believed foreign sessions had been ended.

**`method` and `issuer` on `twoFactor.enable`.** If you pass `method: 'otp'` (email/SMS codes),
confirm you now get OTP rather than TOTP; if you pass a custom `issuer`, confirm it appears as
the label in the authenticator app instead of your app name.

### 3. Retire a hand-rolled reset flow

If your project built its own password-reset page against `useLtAuthClient()` or raw `$fetch`,
replace it. That gap is why these methods now exist:

```typescript
// BEFORE — reaching past the composable
const authClient = useLtAuthClient();
await authClient.requestPasswordReset({ email, redirectTo });

// AFTER
const { requestPasswordReset, resetPassword } = useLtAuth();
await requestPasswordReset({ email, redirectTo });
await resetPassword({ newPassword, token });
```

**Check for a hand-rolled hash while you are in there.** A reset page written directly against the
endpoint sometimes re-implements the SHA256 step, or forgets it. Both are wrong now: the wrappers
hash, so an extra hash produces `sha256(sha256(password))` and a missing one stores a credential
that sign-in can never match. Search your app for `sha256`, `crypto.subtle.digest` and
`digest('hex')` on any password path — there should be no hits.

### 4. Build `redirectTo` as an absolute URL

```typescript
// In an lt starter project — `appUrl()` is auto-imported from app/utils/app-origin.ts
// (it lives in the STARTER, not in this package) and throws rather than returning
// something relative.
redirectTo: appUrl('/auth/reset-password', config.public.siteUrl),

// Anywhere else
redirectTo: new URL('/auth/reset-password', config.public.siteUrl).toString(),
```

Better Auth resolves this value against the **API** origin. A relative path therefore lands on the
API host, where the route does not exist, and the request answers 403 `INVALID_REDIRECT_URL` —
no mail sent, nothing visible in the browser.

**Security, not just plumbing:** the resulting link carries a live single-use reset token. Never
build `redirectTo` from `route.query`, a referrer, or a form field. An attacker-chosen value is
account takeover rather than a phishing redirect, and the server's `trustedOrigins` allowlist is
the only thing standing in the way — so do not widen it, and never set a wildcard.

### 5. Confirm your form enforces a minimum password length

Not new in 1.16.0, but it is the moment to check, because most people assume the server does it.

better-auth validates `minPasswordLength` against the value it **receives**. This library hashes
client-side, so that value is always a 64-character hex string and the check passes on every path.
nest-server 11.38.0 adds a raw-value check for plaintext clients and deliberately skips anything
matching `^[a-f0-9]{64}$` — that is, skips us.

**The form schema is the only place the rule can live.** The lt starters use `v.minLength(8)` on
register, setup and reset. If a rule like that is ever removed on the grounds that "the server
validates it", nothing will catch it.

## What changed in the types, and why nothing breaks

1.15.1 reverted a type-surface change that broke consuming projects, so this deserves an explicit
answer.

The auth parameter types moved from closed shapes (`{ currentPassword: string; newPassword: string }`)
to generics constrained by those same shapes. A generic parameter accepts everything the closed
shape accepted, plus objects carrying extra properties — which is the point, since forwarding
those extras is the bug fix. Interface-typed variables, `Ref<T>.value`, Valibot `InferOutput<>`
shapes and fresh object literals all compile; `test/auth-types.test-d.ts` asserts each of them, and
`pnpm test` typechecks it.

One thing is now **rejected** that previously compiled — passing a credential field that does not
belong to the method:

```typescript
// TS error, deliberately: `password` is not this method's credential and would travel
// unhashed in the request body, into proxy logs and error reporters.
await changePassword({ currentPassword, newPassword, password: plaintext });
```

If you hit that, you have found a real bug in the calling code.

The return type stays `Promise<unknown>`, unchanged. Widening it to better-auth's
`{ data, error }` result would be genuinely useful, but this release line has already had two
type-surface incidents (1.15.0 narrowing, 1.16.0's intermediate `& Record<string, unknown>`), and a
third change at the same boundary in the same release is a bad trade. It is deferred with its own
type test rather than done in a hurry.

## Troubleshooting

**"Reset mail never arrives, and there is no error in the browser."**
`redirectTo` is relative, or points at an origin the server does not trust. Check the API response
for a 403 `INVALID_REDIRECT_URL`, and check `betterAuth.trustedOrigins` on the backend. Note the
special case: with `cors.enabled: false`, nest-server's trusted-origin list resolves to an empty
array and only its own `baseURL` is accepted — such a project must set
`betterAuth.trustedOrigins` explicitly.

**"The user cannot log in with the password they just set."**
A credential-store desync: something on the reset path hashed differently from sign-in. Look for a
hand-rolled reset page (step 3), or a double hash. Server-side, this class of failure is what
nest-server 11.38.0's reset normalisation addresses for plaintext clients.

**"`revokeOtherSessions` still does not end other sessions."**
Confirm the upgrade actually landed (`pnpm ls @lenne.tech/nuxt-extensions`) and that the option is
on the `changePassword` call rather than in the second `options` argument.

**A type error mentioning `never` on a password field.**
Intended — see the types section above. You are passing a credential field the method does not own.

## Rollback

```bash
pnpm add @lenne.tech/nuxt-extensions@1.15.1
```

The runtime is compatible in both directions and no data shape changed, so a rollback is safe. You
lose the two composable methods, and `changePassword` silently drops `revokeOtherSessions` again —
which matters if you shipped a "sign out everywhere" affordance in the meantime.
