# Migration Guide: 1.17.x → 1.18.0

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | **Yes, at build time only.** Four more methods stop being declared: `twoFactor.getTotpUri`, `twoFactor.sendOtp`, `twoFactor.verifyOtp`, `signIn.social`. All four already threw at runtime. |
| **Bugfixes** | `setUser()` accepts Better Auth's session user unchanged — no more `image: null` type error. |
| **Migration Effort** | **None for most projects.** If you upgraded to 1.17.0 without a typecheck error, this one is a version line. |
| **Cross-repo** | **No.** |

---

## Why this is a second release and not part of 1.17.0

1.17.0 removed the `...baseClient` spread that made the client's type promise methods it did not
have. It removed it in one place. The same spread sat in three sub-objects — `signIn`, `signUp`,
`twoFactor` — and those are proxies in exactly the same way:

```js
Object.keys(client.twoFactor)          // []
Object.keys({ ...client.twoFactor })   // []
```

So four methods survived the release that existed to remove them. The guard shipped with 1.17.0
could not see it: it asserted on the client's TOP-LEVEL keys, and `twoFactor` is present at the top
level whatever it contains.

Worth stating plainly, because it is the more useful half: the fix for that guard is not "check the
sub-objects too". A runtime test cannot guard this at all. Re-adding the spread leaves the runtime
suite green, because against a proxy the spread is inert there as well — a runtime guard can only
observe what the spread DOES, which is nothing, never what it PROMISES. 1.18.0 therefore asserts the
type surface in `test/auth-types.test-d.ts`, where reintroducing a spread fails.

## Steps

### 1. Update the package

```bash
# in projects/app
pnpm add @lenne.tech/nuxt-extensions@1.18.0
```

### 2. Build once

```bash
pnpm run typecheck
```

**If it passes, you are done.** If it fails, it will be on one of these four:

| Method | What to do |
|---|---|
| `twoFactor.getTotpUri` | The TOTP URI is already in the response of `twoFactor.enable()` — use that. Only re-displaying the QR later needs the endpoint; say so and it gets a line. |
| `twoFactor.sendOtp` / `verifyOtp` | Email/SMS second factor. No project in the stack uses it yet; ask before building around it. |
| `signIn.social` | Requires `socialProviders` configured server-side, which `@lenne.tech/nest-server` does not set today. |

Each of them was `undefined` at runtime before this release, so a call could not have been working.

### 3. Optional: drop your `image` normalisation

If you combined `getSession()` with `setUser()`, you wrote something like this to get past a type
error:

```ts
// no longer needed
setUser({ ...session.user, image: session.user.image ?? undefined });
```

`setUser` now accepts `LtUserInput` and normalises `null` itself:

```ts
const { data } = await useLtAuthClient().getSession();
if (data?.user) setUser(data.user);
```

`LtUser.image` stays `string | undefined` on purpose. Widening it would have moved the problem
rather than solved it: everyone who only READS `user.image` would have gained a second empty case
to handle, so that the few who write it could skip one line.

## Under the hood

The client's type surface is asserted from the outside now — both that it does NOT declare what it
cannot deliver, and that it still declares everything it does. A guard that only forbids would be
satisfied by an empty client, which is the failure mode one release further along.
