# Migration Guide: 1.18.x → 1.19.0

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | **Yes, for two setups only.** A relative TUS endpoint is now a path on the API, not on the app. Affected: a project that routes uploads through its own same-origin proxy, and an endpoint that carries the dev-proxy prefix itself (`'/api/files/upload'`). |
| **New** | `ltExtensions.tus.resolveAgainstApi` (default `true`). `LtUploadItem.fileId`: the id of the stored file, from the `X-File-Id` response header. |
| **Bugfixes** | Uploads work in `nuxt dev` (tus-js-client's CommonJS dependency `url-parse` is pre-bundled). `useLtTusUpload({ endpoint: undefined })` keeps the default endpoint instead of starting no upload. `useLtFile()` no longer derives its file routes from a `/tus` endpoint. |
| **Migration Effort** | **One config line** for projects on the lt starter: set `tus.defaultEndpoint: '/tus'`. |
| **Cross-repo** | **`fileId` needs `@lenne.tech/nest-server` 11.42.13+**, which sends `X-File-Id`. Everything else works with any version. |

---

## What changed, and why

### Relative endpoints go to the API

`tus.defaultEndpoint` (and `useLtTusUpload({ endpoint })`) used to be passed to tus-js-client as
written. A relative path therefore went to the origin the page came from: the app. Nothing there
serves TUS, so the upload answered 404 — in the starters too, whose `'/files/upload'` reached the
Nuxt server.

A relative endpoint is now resolved the way the auth and AI requests are (`buildLtApiUrl`):

| Environment | `'/tus'` becomes |
|---|---|
| Deployed, `lt dev up` | `NUXT_PUBLIC_API_URL` + `/tus`, e.g. `https://api.example.com/tus` |
| Local dev proxy (`NUXT_PUBLIC_API_PROXY=true`) | `/api/tus` |
| No API URL configured | `/tus` on the app origin, plus the usual "Set NUXT_PUBLIC_API_URL" warning |

Absolute endpoints (`https://…`, `//host/…`) are never rewritten. The switch
`ltExtensions.tus.resolveAgainstApi: false` restores the old behaviour.

### `fileId` replaces "the last segment of `url`"

`item.url` is the TUS upload resource. Projects took its last segment as the file id, but that is
the TUS upload id, so every link built from it answered 404. nest-server 11.42.13+ names the stored
file in the `X-File-Id` header of the response that completes the upload; it is now
`item.fileId`, set before `onSuccess` fires.

## Steps

### 1. Update the package

```bash
pnpm add @lenne.tech/nuxt-extensions@1.19.0
```

### 2. Point the endpoint at nest-server's TUS route

nest-server serves TUS at `/tus` unless its `tus.path` says otherwise. The module's own default is
still `'/files/upload'`, which with this release resolves to `<API>/files/upload` — in a
nest-server-starter API that is the multipart upload route, not TUS. Set it explicitly:

```typescript
// nuxt.config.ts
ltExtensions: {
  tus: {
    defaultEndpoint: '/tus',
  },
},
```

### 3. Check whether one of the two breaking setups is yours

| Your setup | What to do |
|---|---|
| A same-origin proxy (nginx, Nitro route, …) forwards a path on the app domain to the API, and the endpoint names that path | `resolveAgainstApi: false` — the endpoint stays on the app origin as before |
| The endpoint carries the dev-proxy prefix itself, e.g. `'/api/files/upload'` | Drop the prefix (`'/tus'`). The resolution adds `/api` in proxy mode; keeping it yields `/api/api/…` |
| An absolute URL | Nothing |
| A relative path that never worked (404 on the app) | Nothing beyond step 2 |

### 4. Use `fileId` for file references

```typescript
useLtTusUpload({
  onSuccess: (item) => {
    // before: item.url?.split('/').pop() — the TUS upload id
    emit('uploaded', item.fileId);
  },
});
```

`fileId` is optional: it is undefined against an older nest-server, and when a project overrides
`CoreTusService.onUploadComplete()` without calling `super.onUploadComplete(upload)` (e.g. one that
stores the file itself). Do not fall back to the last segment of `url` then — that is the upload id,
and `/files/id/<it>` answers 404.

## Under the hood

- After the first request, tus-js-client sends the remaining chunks to the `Location` URL the server
  returns, not to the endpoint again. Where that URL points behind a proxy is decided by nest-server
  (`tus.path`, `tus.relativeLocation`); see "Upload URLs (11.42.9+)" in nest-server's TUS module README.
- The endpoint is resolved when an upload is created, i.e. in the browser. The server-only
  `NUXT_API_URL` therefore never ends up in an upload URL.
- `useLtFile()` derives its base path from the TUS endpoint only when that ends in `/upload`
  (`'/files/upload'` → `'/files'`, unchanged). Any other endpoint leaves the file routes at `/files`.
