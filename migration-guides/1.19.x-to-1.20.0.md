# Migration Guide: 1.19.x → 1.20.0

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | **Install-level only.** The `better-auth` and `@better-auth/passkey` peer range narrows from `>=1.7.7 <1.8.0` to `>=1.7.12 <1.8.0`. A project resolving 1.7.7 to 1.7.11 gets a peer conflict (`ERESOLVE` under npm, a peer warning under pnpm). No API of this module changed. |
| **New** | Nothing. |
| **Bugfixes** | `waitForElement()` (`@lenne.tech/nuxt-extensions/testing`) no longer hangs until the test times out when an animation is cancelled. An error inside the auth interceptor's 401 handling is logged instead of surfacing as an unhandled promise rejection. Nothing to migrate for either. |
| **Migration Effort** | Pin `better-auth` (and `@better-auth/passkey`, if you use passkeys) to `1.7.12` on **both** sides, then update both frameworks. No code changes. |
| **Cross-repo** | **Lock-step with `@lenne.tech/nest-server` 12.0.0**, which declares the same range. The API and the app must resolve the same better-auth version. |

The major digit tracks Nuxt (1.x is Nuxt 4), so a narrowed peer range ships as a minor.

---

## Why the floor moved

better-auth 1.7.12 changed how its JWT plugin verifies tokens: it now uses the algorithm of the
stored key instead of the algorithm the token names in its own header
([better-auth#11925](https://github.com/better-auth/better-auth/pull/11925)). Trusting the header
is the classic algorithm-confusion pattern. No advisory was published, so `pnpm audit` stays
silent about older versions. Do not read a clean audit as "not affected".

The verification runs in the API, not in this module. The floor still moves here because both
frameworks declare a byte-identical range. That rule exists because an api and an app on different
better-auth versions once broke every 2FA activation while both projects' checks were green.

## Steps

### 1. Pin better-auth on both sides

In a fullstack monorepo, pin it workspace-wide:

```yaml
# pnpm-workspace.yaml (workspace root)
overrides:
  better-auth: 1.7.12
  '@better-auth/passkey': 1.7.12
```

For a standalone app:

```bash
pnpm add better-auth@1.7.12
pnpm add @better-auth/passkey@1.7.12   # only if you use passkeys
```

### 2. Update both frameworks

```bash
# projects/app
pnpm add @lenne.tech/nuxt-extensions@1.20.0
# projects/api: follow the nest-server 11.43.x → 12.0.x migration guide
```

nest-server 12.0.0 is a major release (NestJS 12) with its own guide. If the API cannot move yet,
the pin from step 1 still satisfies nest-server 11.x, whose range `>=1.7.7 <1.8.0` admits 1.7.12.
That combination works at install time, but 11.x was only tested against 1.7.7.

### 3. Check what each side resolves

```bash
pnpm why better-auth
```

Every line must show 1.7.12. Two versions means one side escaped the pin.

### 4. Walk the auth flows once

Automated checks compare declarations. They cannot see a broken protocol. After the upgrade, sign
in with a password user, sign out and in again with 2FA if you use it, and make one authenticated
request after the JWT has expired (15 minutes by default) to see the token refresh work.

## Troubleshooting

**`ERESOLVE` or a peer warning that mentions better-auth**
Expected. Something still resolves better-auth 1.7.7 to 1.7.11, usually the API on an older
lockfile. Do step 1 and reinstall. Do not widen the range locally.

**`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` for better-auth 1.7.12**
Only possible if your project sets `minimumReleaseAge` above the default. 1.7.12 was published on
2026-10-20. Wait until it clears your gate rather than excluding it.

**A new warning about a JWT without issuer or audience in the API log**
That is better-auth 1.7.12 itself: it now warns when it signs or verifies a JWT that carries
neither. It is a server-side configuration matter and does not come from this module.
