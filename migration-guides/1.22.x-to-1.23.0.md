# Migration Guide: 1.22.x → 1.23.0

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | **Install-level only.** The `better-auth` and `@better-auth/passkey` peer range narrows from `>=1.7.12 <1.8.0` to `>=1.7.16 <1.8.0`. A project resolving 1.7.12 to 1.7.15 gets a peer conflict (`ERESOLVE` under npm, a peer warning under pnpm). No API of this module changed. |
| **New** | `useLtAiStatus()`: whether the API's AI module is on (`GET /ai/status`, nest-server 12.3.1 or later). See the README, "AI status". |
| **Bugfixes** | None. |
| **Migration Effort** | Pin `better-auth`, `@better-auth/passkey` and `@better-auth/core` to `1.7.16` on **both** sides, then update both frameworks. No code changes. |
| **Cross-repo** | **Lock-step with `@lenne.tech/nest-server` 12.3.1**, which declares the same range. The API and the app must resolve the same better-auth version. |

The major digit tracks Nuxt (1.x is Nuxt 4), so a narrowed peer range ships as a minor.

---

## Why the floor moved

better-auth 1.7.16 closes twelve advisories published on 2026-11-03. Among those that reach a
typical lt project:

- a social sign-in can treat an unverified provider email as verified
  ([GHSA-9hm7-xhfp-cx58](https://github.com/better-auth/better-auth/security/advisories/GHSA-9hm7-xhfp-cx58))
- revoked sessions can stay valid with secondary storage or the cookie cache
  ([GHSA-fvxx-76fc-893x](https://github.com/better-auth/better-auth/security/advisories/GHSA-fvxx-76fc-893x))
- email-change links stay valid after the address changes hands
  ([GHSA-hwq2-v29r-p69r](https://github.com/better-auth/better-auth/security/advisories/GHSA-hwq2-v29r-p69r))
- passkey verification does not enforce origin or user verification
  ([GHSA-gv75-j3v8-3crm](https://github.com/better-auth/better-auth/security/advisories/GHSA-gv75-j3v8-3crm))

It also pins better-call 1.4.5, which closes
[GHSA-23w8-wx9r-vm57](https://github.com/better-auth/better-call/security/advisories/GHSA-23w8-wx9r-vm57)
(high, shared router context). That one is a second layer only: better-auth's own handler builds a
fresh router per request, so the flaw is not reachable through it.

These flaws are in the API, not in this module. The floor still moves here because both frameworks
declare a byte-identical range. That rule exists
because an api and an app on different better-auth versions once broke every 2FA activation while
both projects' checks were green.

At the time of this release the advisories are listed in the projects' own repositories but not
yet in the global advisory database, so `pnpm audit` stays silent about 1.7.15 and older. Do not
read a clean audit as "not affected".

## Steps

### 1. Pin better-auth on both sides

In a fullstack monorepo, pin it workspace-wide:

```yaml
# pnpm-workspace.yaml (workspace root)
overrides:
  better-auth: 1.7.16
  '@better-auth/passkey': 1.7.16
  '@better-auth/core': 1.7.16
```

`@better-auth/core` belongs in the list because the api of a project made from nest-server-starter
depends on it directly (`"@better-auth/core": "1.7.12"` up to nest-server-starter 12.3.0). Left out,
it stays at 1.7.12, passkey 1.7.16 is wired against it, and `pnpm peers check` in the api's `check`
fails with unmet peers for `@better-auth/core`, `better-call` and `@better-fetch/fetch`.

For a standalone app:

```bash
pnpm add better-auth@1.7.16
pnpm add @better-auth/passkey@1.7.16   # only if you use passkeys
```

### 2. Update both frameworks

```bash
# projects/app
pnpm add @lenne.tech/nuxt-extensions@1.23.0
# projects/api
pnpm add @lenne.tech/nest-server@12.3.1
```

If the API cannot move yet, the pin from step 1 still satisfies the range of every nest-server 12.x
(`>=1.7.12 <1.8.0`). Pin it anyway: the fix only works where the API runs 1.7.16.

### 3. Check what each side resolves

```bash
pnpm why better-auth
pnpm why @better-auth/core
pnpm why better-call
pnpm peers check
```

Every line must show 1.7.16 for better-auth and `@better-auth/core` and 1.4.5 for better-call, and
`pnpm peers check` must pass. Two versions means one side escaped the pin.

### 4. Walk the auth flows once

Automated checks compare declarations. They cannot see a broken protocol. After the upgrade, sign
in with a password user, sign out and in again with 2FA if you use it, and make one authenticated
request after the JWT has expired (15 minutes by default) to see the token refresh work.

## Troubleshooting

**`ERESOLVE` or a peer warning that mentions better-auth**
Expected. Something still resolves better-auth 1.7.12 to 1.7.15, usually the API on an older
lockfile. Do step 1 and reinstall. Do not widen the range locally.

**`pnpm peers check` fails on `@better-auth/core`, `better-call` or `@better-fetch/fetch`**
`@better-auth/core` is still at 1.7.12, usually as a direct dependency of the api. Add it to the
overrides of step 1 (or `pnpm add @better-auth/core@1.7.16` in the api) and reinstall.

**`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` for better-auth 1.7.16 or better-call 1.4.5**
They were published on 2026-11-03 around 21:24 UTC, so pnpm's 24h gate holds them until
2026-11-04 21:24 UTC. To take the fix earlier, exempt the exact versions, as both frameworks did:

```yaml
# pnpm-workspace.yaml — remove the entries with your next maintenance
minimumReleaseAgeExclude:
  - '@better-auth/core@1.7.16'
  - '@better-auth/drizzle-adapter@1.7.16'
  - '@better-auth/kysely-adapter@1.7.16'
  - '@better-auth/memory-adapter@1.7.16'
  - '@better-auth/mongo-adapter@1.7.16'
  - '@better-auth/passkey@1.7.16'
  - '@better-auth/prisma-adapter@1.7.16'
  - '@better-auth/telemetry@1.7.16'
  - better-auth@1.7.16
  - better-call@1.4.5
```

After that time the entries are inert, and waiting is the simpler path.
