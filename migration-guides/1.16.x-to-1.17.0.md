# Migration Guide: 1.16.x → 1.17.0

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | **Yes, at build time only.** The auth client's type no longer declares ~13 Better-Auth methods that were `undefined` at runtime. Calling one already threw; now it fails to compile instead. |
| **New Features** | `sendVerificationEmail`, `verifyEmail` and `getSession` are available on `useLtAuthClient()`. |
| **Bugfixes** | A raw `$fetch` error passed to `translateError()` now translates instead of showing the HTTP transport line. |
| **Migration Effort** | **None for most projects.** Only code that calls one of the listed methods is affected, and that code is already broken at runtime. |
| **Cross-repo** | **No.** `@lenne.tech/nest-server` does not need to be upgraded. |

---

## Why a breaking change is still a minor

The MAJOR digit of this package tracks the **Nuxt** major it targets — `1.x` is Nuxt 4 — so it
moves when Nuxt moves and not before. Everything of our own ships in a minor, breaking changes
included. The version number is not making a promise here that this guide takes back; it is
carrying a different meaning than strict semver would give it.

---

## What actually changed

`createLtAuthClient()` used to begin with:

```ts
return {
  // Spread all base client properties and methods
  ...baseClient,
  useSession: baseClient.useSession,
  // …
};
```

That comment was wrong, and measurably so. Better Auth builds its client through
`createDynamicPathProxy` — a `new Proxy(function () {}, { apply, get })` over an empty function,
with no `ownKeys` trap. Every method is fabricated inside `get`, so the proxy owns no enumerable
properties and a spread copies none of them:

```js
Object.keys(client)          // []
Object.keys({ ...client })   // []
client.sendVerificationEmail // function   ← fabricated on access
({ ...client }).sendVerificationEmail // undefined
```

Everything that worked did so because it was listed by name **after** the spread. The spread line
contributed nothing at runtime.

At the type level it contributed everything, because TypeScript spreads declared members whatever
the runtime does. `LtAuthClient` is `ReturnType<typeof createLtAuthClient>`, so the published type
promised methods the object never had. Autocomplete offered them, the compiler accepted them, and
they were `undefined` when called.

That is the failure this release removes: not a missing feature, but a false promise. Three
separate projects met the resulting `TypeError`, concluded the library did not support the call,
and rebuilt it against raw `$fetch`.

## Steps

### 1. Update the package

```bash
# in projects/app
pnpm add @lenne.tech/nuxt-extensions@1.17.0
```

### 2. Build once and read the errors

```bash
pnpm run typecheck
```

**If it passes, you are done.** Nothing else in this release requires action.

If it fails, it will be on a call to one of these — every one of them was already throwing
`TypeError: … is not a function` at runtime:

`updateUser`, `deleteUser`, `changeEmail`, `linkSocial`, `unlinkAccount`, `listAccounts`,
`listSessions`, `revokeSession`, `revokeSessions`, `revokeOtherSessions`, `accountInfo`,
`getAccessToken`, `refreshToken`

Two of them are not merely absent from this client but switched off in the backend:
`@lenne.tech/nest-server` does not set `user.deleteUser.enabled` or `user.changeEmail.enabled`, so
Better Auth's routes answer with an error regardless of how you call them. Account deletion runs
through nest-server's own `/users` endpoints.

For the rest, call the endpoint directly with `ltAuthFetch` for now, and open an issue saying which
one you need. Each method on the list is a promise this package then keeps across versions, so they
are added when a caller exists rather than pre-emptively.

### 3. Optional: retire your email-verification workaround

If you built verification against raw `$fetch` — likely, because the methods did not exist — you
can now use the client:

```ts
const authClient = useLtAuthClient();

// Send (or re-send). `callbackURL` goes INTO the mail.
await authClient.sendVerificationEmail({
  email,
  callbackURL: new URL('/auth/verify-email', config.public.siteUrl).toString(),
});

// Verify, with the token from the query string.
const { data } = await authClient.verifyEmail({ query: { token } });
```

Two things to keep, both of which cost somebody a debugging session:

- **`callbackURL` must be absolute.** Better Auth resolves a relative value against the **API**
  origin, so `/auth/verify-email` becomes `api.<host>/auth/verify-email`, where the route does not
  exist. The mail goes out and the user follows a link to a 404. This client passes the value
  through untouched on purpose — normalising it would hide the mistake until the next caller made
  it somewhere you cannot see.
- **Do not pass `callbackURL` when VERIFYING.** The endpoint branches on it: with one it answers
  `302` to that URL, carrying neither token nor status; without one it answers `{ status: true }`
  as JSON. It is not the same parameter as the one that goes into the mail, and confusing the two
  produces a page that reports failure on success.

### 4. Optional: drop your error-unwrapping helper

`translateError()` now reads the response body of a fetch error before falling back to the thrown
message, so this works directly:

```ts
try {
  await $fetch(url, { method: 'POST', body });
} catch (err) {
  // Previously showed: [POST] "/iam/reset-password": 400 Bad Request
  // Now shows the translated backend message.
  toast.add({ description: translateError(err), color: 'error' });
}
```

While you are in that code, two things worth checking:

- **`translateError(x) || 'Fallback'` never reaches the fallback.** An unrecognised message is
  returned unchanged, so the result is non-empty and truthy. The `||` reads like a safety net,
  catches nothing, and hides that the untranslated English text is what the user sees. One project
  had it in six pages.
- **Branch on the error CODE, not the message.** Better Auth answers `POST /reset-password` with
  five different errors under the same `400`.

## Under the hood

- `pnpm peers check` joined the `check` chain. `pnpm audit` and a peer check answer different
  questions, and a tree can pass one while failing the other — which is exactly what happened while
  preparing this release.
- A transitive `@tiptap/*` advisory is pinned out via workspace overrides. It arrives through a
  devDependency and never reached the published package; consuming projects are unaffected and need
  no override of their own.
