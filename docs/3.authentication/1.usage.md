```vue
<script setup>
// Auth composable (auto-imported)
const {
  user,
  isAuthenticated,
  isAdmin,
  isLoading,
  signIn,
  signOut,
  authenticateWithPasskey,
  registerPasskey,
  twoFactor,
  changePassword,
  requestPasswordReset,
  resetPassword,
} = useLtAuth();

// Login with email/password. For an account with 2FA, nest-server answers
// `{ requiresTwoFactor: true }` (Better-Auth's own `twoFactorRedirect` makes the two-factor
// client plugin navigate to `auth.twoFactorRedirectPath` by itself; nest-server does not send it).
async function handleLogin(email: string, password: string) {
  const { data } = (await signIn.email({ email, password })) as {
    data?: { requiresTwoFactor?: boolean; twoFactorRedirect?: boolean } | null;
  };
  if (data?.requiresTwoFactor || data?.twoFactorRedirect) {
    await navigateTo('/auth/2fa');
  }
}

// On the 2FA page: finishes the sign-in (user, cookie session, JWT from /iam/token)
async function handleTotp(code: string) {
  const { error } = (await twoFactor.verifyTotp({ code })) as { error?: { message?: string } | null };
  if (!error) {
    navigateTo('/dashboard');
  }
}

// Passkey login
async function handlePasskeyLogin() {
  const result = await authenticateWithPasskey();
  if (result.success) {
    navigateTo('/dashboard');
  }
}
</script>

<template>
  <div v-if="isAuthenticated">
    Welcome, {{ user?.name }}!
    <button @click="signOut()">Logout</button>
  </div>
</template>
```

## Two-factor sign-in, and what `lt-jwt-token` may hold

Finish a sign-in that stopped at the second factor with `useLtAuth().twoFactor.verifyTotp()` or
`verifyBackupCode()`. They put the user into the auth state on the cookie session and fetch the
JWT from `/iam/token`. When the answer already carries a JWT, they take it as it is, with no
`/iam/token` request. nest-server sends one where the body may carry a token (`cookies: false`,
or `exposeTokenInBody`): the JWT of the session that is valid after the answer.

- **Never store the `token` of a 2FA or passkey answer yourself.** Better-Auth answers
  `verify-totp` and `verify-backup-code` with `{ token, user }`, and `passkey/verify-authentication`
  with `{ session, user }`. That token is its session token, the value the API keeps in the
  httpOnly cookie. Stored as the "JWT", it lands in the readable `lt-jwt-token` cookie, where any
  script on the page can take it for the session's whole lifetime. A JWT in the answer is stored
  by the client itself (below).
- **`lt-jwt-token` holds a JWT or nothing.** `jwtToken`, `setLtJwtToken()` and the sign-in
  methods refuse anything else; `isLtJwtShaped()` (from `/lib`) is the test, the same as
  nest-server's `isJwtShaped`.
- **A value found there that is not a JWT is deleted** on the next start or read, along with the
  JWT mode it came with. The httpOnly session cookie keeps the user signed in.
- **`setUser(user, 'jwt')` without a stored JWT signs in on the cookie session** and fetches the
  JWT. A hand-written 2FA page that stored the body token therefore still works, without the
  leak; move it to the helpers anyway.
- **`setUser(user)` without a mode keeps the auth mode when it updates the signed-in user**
  (same `id`), as `setUser({ ...user.value, twoFactorEnabled: true })` after turning 2FA on does.
  Any other user starts on the cookie session (since 4.0.5; before, every call without a mode
  meant cookie mode, and a settings page in JWT mode stopped sending its JWT).
- **`useLtAuthClient().twoFactor.verifyTotp()`, `verifyBackupCode()`, `enable()`, `disable()`
  and `changePassword()` return no session token.** A JWT in the answer stays, and the client
  stores it in `lt-jwt-token` (since 4.0.5); the auth mode is left as it is. From nest-server
  12.11.0 on, every JWT is bound to its session. Turning 2FA on or off, or changing the password
  with `revokeOtherSessions`, replaces that session, and the API refuses the JWT stored before. A
  settings page that does this through the client keeps working in JWT mode. Turning 2FA off
  needs nest-server 12.11.1 for that: 12.11.0 answers `two-factor/disable` without the new JWT.
  With `throw: true` the client reads no answer and stores nothing.
- **`authenticateWithPasskey()` returns no `session`.**

## Sign-in through a social provider

`useLtAuth().signIn.social()` (since 4.0.3; `useLtAuthClient().signIn.social()` is the same call
without the auth state) signs in through a provider the API configured, for example Microsoft
Entra ID for single sign-on (`betterAuth.socialProviders` in nest-server). `GET /iam/features`
lists the enabled providers as `socialProviders`; `useLtAuth().features` holds that answer, so a
login page can show one button per entry.

The same answer also reports `emailAndPassword` (nest-server 12.11.0 or later). When it is `false`,
the API offers no sign-in with email and password: hide that form, the "forgot password" link and
registration. An older API does not send the field, so treat a missing value as `true`.

Both shapes go to `POST <basePath>/sign-in/social`:

- **Redirect, the usual one.** The answer is the provider's authorization URL, and Better Auth's
  client navigates there: the page is left, and nothing is stored yet. The provider sends the
  browser to the API, which sets the session cookie and redirects to `callbackURL`. The user
  arrives through `validateSession()` on the page behind it.
- **ID token**, for an app inside a host that already knows the user (Microsoft Teams, a native
  shell). With `idToken` the API answers `{ user }` at once, without navigation. `useLtAuth()` signs
  the user in on the cookie session and fetches the JWT from `/iam/token`, as after 2FA. The
  session token Better Auth puts into that answer is removed, as in the 2FA answers. This covers
  the default `{ data, error }` answer only: with `throw: true` (as `options` or in `fetchOptions`)
  the body comes back unchanged, token included, and an `onSuccess` hook sees the answer before the
  token is removed. **nest-server 12.11.0 and later refuse this shape** with
  `ID_TOKEN_NOT_SUPPORTED` unless the provider sets `disableIdTokenSignIn: false`. The redirect
  shape is not affected.

```vue
<script setup lang="ts">
const { features, signIn } = useLtAuth();
const config = useRuntimeConfig();

const providers = computed(() => (Array.isArray(features.value.socialProviders) ? features.value.socialProviders : []));

// Interactive: the provider shows its account picker.
async function signInWith(provider: string) {
  await signIn.social({
    additionalParams: { prompt: 'select_account' },
    callbackURL: new URL('/auth/callback', config.public.siteUrl).toString(),
    errorCallbackURL: new URL('/auth/login', config.public.siteUrl).toString(),
    provider,
  });
}
</script>
```

```vue
<!-- pages/auth/callback.vue: the session cookie is set, the user is not loaded yet -->
<script setup lang="ts">
const { validateSession } = useLtAuth();

onMounted(async () => {
  const signedIn = await validateSession();
  await navigateTo(signedIn ? '/app' : '/auth/login', { replace: true });
});
</script>
```

- **A silent attempt is `additionalParams: { prompt: 'none' }`.** The provider answers without
  showing anything: with the session when the user has one there, otherwise through
  `errorCallbackURL` with `?error=login_required` (or `interaction_required`). That way back is the
  only one, so the page behind it must not start the attempt again: remember it per tab, and do
  not try silently after an explicit sign-out, or the user is signed in again at once.
  nuxt-base-starter does both on its login page.
- **`?error=` on `errorCallbackURL` is a code from the provider or from Better Auth**
  (`access_denied`, `signup_disabled`, …). Map it to your own text. Never render `error_description`
  or anything else from the query: anybody can put text there and send the link around.
- **`callbackURL` and `errorCallbackURL` must be absolute URLs of a trusted origin, and never come
  from user input.** Better Auth resolves a relative value against the API origin, like
  `redirectTo` (see "Password Change and Reset"), and checks the result against `trustedOrigins`,
  which is all that stands between a value from `route.query` and a redirect to another site. Build
  both from your own origin and a fixed path; a deep link the user should land on afterwards goes
  into their query only after it was validated (nuxt-base-starter: `safeRedirectTarget()`).
- `additionalParams` applies to this request only, `loginHint` suggests an account, and
  `disableRedirect: true` answers the URL without navigating. `LtSocialSignInParams` documents every
  field.

**An inline profile photo is not kept in the auth state.** Better Auth's Microsoft provider stores
the user's photo in `user.image` as a `data:` URL. In the `lt-auth-state` cookie a few KB of it push
the cookie past the browser's limit of 4096 bytes; the browser drops it without an error, and the
next page load reads as a logout. So `useLtAuth().user.value.image` is `undefined` for such a user,
while an `http(s)` URL or a path stays. Where you render an avatar, read the photo from the session
answer (`GET <basePath>/get-session`, e.g. `useLtAuthClient().getSession()`). An API that does not
need the photo sets `disableProfilePhoto: true` on the Microsoft provider.

## Authenticated requests: `fetchWithAuth` and `ltAuthFetch`

`useLtAuth().fetchWithAuth` and `ltAuthFetch` (from `/lib`, also used by the Better-Auth client,
the AI composables and offline sync) run through one implementation.

- **JWT mode sends `Authorization: Bearer <jwt>`.** `ltAuthFetch` always sends the cookies as well,
  so nest-server (>= 11.13.1) falls back to the session cookie when the bearer fails.
  `fetchWithAuth` sends them in JWT mode only to passkey, 2FA and `/get-session`.
- **A 401 while signed in fetches a JWT once and retries the request once.** In cookie mode that
  is the switch to JWT; in JWT mode it renews an expired JWT, which lives 15 minutes while the
  session lasts 7 days. Requests that fail in the same burst share one `GET <basePath>/token`. A
  401 that survives the fresh token reaches the caller unchanged, and so does a 401 in JWT mode from
  Better-Auth's own routes (sign-in, 2FA, passkey): there it is the flow's verdict, and a wrong
  password or code must not be sent twice.
- **The JWT comes from `auth.basePath`.** Without an argument, `ltAuthFetch`, `createLtAuthFetch()`
  and `attemptLtJwtSwitch()` read it from the module config; they used to fetch it from `/iam`
  whatever was configured. A path passed explicitly still wins.
- **An API without JWT is not asked for one.** When `GET <basePath>/features` reports `jwt: false`
  (nest-server with `betterAuth.jwt: false`, whose `/token` answers 404), neither a sign-in, a
  session check nor a 401 requests `/token`: the app stays on the cookie session, and a 401 reaches
  the caller unchanged. Nothing to configure in the app; the features request `useLtAuth()` makes on
  its first client-side call decides, and a JWT request at app start waits for it. Features a page
  fetched during SSR (`await fetchFeatures()` in `import.meta.server`) count the same, from the
  payload. An API that reports `jwt: true`, or no `jwt` at all, is asked as before.

## Server-side rendering: backend calls are anonymous

During SSR, `ltAuthFetch`, the AI composables and offline sync call the API **without** a session:
on the server `getLtAuthMode()` is `'cookie'`, `getLtJwtToken()` is `null` and `isLtAuthenticated()`
is `false`. The one exception is `useLtAuth().fetchWithAuth` (see the last point below). That is deliberate. The auth helpers are module singletons shared by every request a
Nitro process renders, so they may not carry one request's cookies. And the session cookie
(`iam.session_token`) belongs to the API host: nest-server sets it host-only unless
`crossSubDomainCookies` is configured, so the app server never receives it. `validateSession()` on
the server therefore relies on the `lt-auth-state` cookie only, which is a display cache, not proof
of a session.

For pages that show user data:

- **Load it in the browser.** `useAsyncData(key, fetcher, { server: false })` or `onMounted`, with a
  skeleton or loading state for the first paint. This is what nuxt-base-starter does.
  `useLazyAsyncData` alone is not enough: `lazy` only stops it from blocking navigation, the
  fetcher still runs during SSR, and its anonymous answer (a 401 or the public subset) goes into
  the payload, which the browser does not fetch again. Add `server: false` there too.
- **Render only public data on the server**, and never decide access there: an SSR guard that reads
  `lt-auth-state` decides what to render, the API decides what the user may see.
- If a page truly needs user data in the SSR HTML, that needs a server route of the app that
  forwards the request's own session to the API, set up per project together with a shared cookie
  domain. `ltAuthFetch` does not do it.
- **`useLtAuth().fetchWithAuth` during SSR is not anonymous.** It reads the request's cookies through
  `useCookie`, and in JWT mode (the normal state after sign-in) it sends the request's `lt-jwt-token`
  as the bearer. It cannot renew that token on the server, so the call works until the JWT expires
  (15 minutes) and then answers 401. Do not use it for SSR-rendered user data, and never cache
  (`swr`, `isr`, a CDN) a route whose SSR output went through it: one user's data would be served to
  the next.

## Admin detection (`role` vs `roles`)

`isAdmin` accepts **both** user shapes, so the same frontend works against either backend:

| Backend | User shape | `isAdmin` is `true` when |
|---------|------------|-------------------------|
| `@lenne.tech/nest-server` | `roles: ['admin']` — core Better-Auth additionalField (`type: 'string[]'`), no singular `role` | `roles` contains `'admin'` |
| Better-Auth admin plugin | `role: 'admin'` — single role | `role === 'admin'` |

```vue
<script setup>
const { isAdmin } = useLtAuth();
</script>

<template>
  <NuxtLink v-if="isAdmin" to="/admin">Admin</NuxtLink>
</template>
```

> **`isAdmin` is a UX gate, not an authorization boundary.** It reads the client-side `lt-auth-state` cookie cache, which is not httpOnly and therefore user-writable. Use it to decide what to *render*; always enforce admin rights server-side (`@Restricted(RoleEnum.ADMIN)` in nest-server).
>
> The `auth.enableAdmin` option toggles the Better-Auth **admin client plugin** (user-management calls such as `admin.listUsers()`). It does **not** control `isAdmin` — role detection works regardless of that flag.

For roles other than admin, use `hasRole(role)` / `hasAnyRole(...roles)`. They apply the exact same both-shapes union and `Array.isArray` guard as `isAdmin` (which is itself just `hasRole('admin')`), so you never need the unguarded `user.value?.roles?.includes(...)`:

```vue
<script setup>
const { hasRole, hasAnyRole } = useLtAuth();
</script>

<template>
  <button v-if="hasRole('editor')">Edit</button>
  <NuxtLink v-if="hasAnyRole('admin', 'editor')" to="/manage">Manage</NuxtLink>
</template>
```
